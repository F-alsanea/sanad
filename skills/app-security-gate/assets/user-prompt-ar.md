# برومبت المراجعة الأمنية — انسخه كما هو

تحقق من أمان هذا التطبيق وفق بوابة fail-closed. لا تطبع قيمة أي سر. لا تعدّل ملفاً قبل أن أعرض التقرير وتأتي موافقتي بعبارة نفّذ، إلا إذا أمرتك بالتنفيذ في نفس الرسالة.

افحص البوابات التالية بالدليل (ملف:سطر أو مخرج أمر)، لا بالنية:

1) إخفاء مفاتيح الـ API
- لا مفتاح سري في كود العميل أو المستودع أو الصور أو اللوج.
- المسموح في العميل فقط مفتاح مصمَّم ليكون عاماً.

2) إزالة الأسرار من سجلات Git
- افحص HEAD والتاريخ. حذف الملف اليوم لا يكفي.
- إن وُجد سر في التاريخ: اعتبره محروقاً، اطلب تدويره، ولا تعِد كتابة التاريخ إلا بأمر صريح.

3) كشف مفتاح قاعدة البيانات العام فقط
- ممنوع service_role أو سلسلة اتصال بصلاحية واسعة في المتصفح أو التطبيق.
- المفتاح الواسع على الخادم فقط من متغيرات البيئة.

4) تفعيل أمان مستوى الصفوف (Row-Level Security)
- كل جدول فيه صفوف تخص مستخدماً أو مستأجراً له RLS (أو عزل مكافئ).
- سياسة USING (true) على جدول حساس تُعد فشلاً.
- اختبر ذهنياً: مستخدم يغيّر id في الطلب لا يرى صف غيره.

5) تشفير البيانات الحساسة
- كلمات المرور = hash قوي، ليست تشفيراً عكسياً.
- توكنات وأسرار طرف ثالث وPII شديد = تشفير عمودي ومفتاحه ليس في المستودع.
- HTTPS وحده ليس تشفير مخزن.

6) فرض المصادقة من جانب الخادم
- الهوية والصلاحية وملكية الصف تُحسم على الخادم قبل أي استعلام أو كتابة.
- إخفاء رابط الأدمن ليس حماية.
- إن تعذر التحقق: ارفض.

7) تأمين السجلات
- لا توكن ولا كلمة مرور ولا جسم طلب خام ولا Authorization في اللوج أو صفحات الخطأ.

بعد السبع افحص بإيجاز: حقن، XSS، CSRF، رفع ملفات، SSRF، webhooks بلا توقيع، rate limit على الدخول/OTP، CORS بـ * مع credentials، headers الإنتاج.

أخرج:
- قرار كل بوابة PASS / FAIL / UNVERIFIED مع دليل
- مصفوفة Critical / High / Medium / Low
- قائمة أسرار بأنواعها بلا قيم، وهل هي في HEAD أو التاريخ
- خطة إصلاح مرتبة، مع تمييز ما هو غير قابل للتراجع
- لا تقل «التطبيق آمن» إلا إذا البوابات السبع PASS بدليل
